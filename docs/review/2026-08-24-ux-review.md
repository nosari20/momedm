# Môme DM — UX/UI review

Read-only review of the shipped app: parent controller (English) and child launcher (French),
against the screenshots in `docs/images/` and the Compose source under
`app/src/main/java/edu/fnosari/momedm/activities/`. No code was changed. Findings are ordered by
impact; items I could not fully verify from static reading are marked **Question**.

---

## 1. Every parent action can pop an untranslated, developer-language snackbar

**Screens:** any action on `parent-device.png` — Start/Stop child mode, Lock now/Unlock, Choose
allowed apps, install, refresh, add account, change content restrictions, change advanced app
settings, rename does not count (no command sent).

**The problem.** `ControllerViewModel.kt:72` builds the toast the parent sees after *every*
command result:

```kotlin
_events.emit(app.getString(R.string.child_result, "${app.getString(if (r.ok) R.string.result_ok else R.string.result_err)}: ${r.msg}"))
```

`r.msg` comes straight from the child device's `CommandExecutor.kt`, which fills it with raw,
hardcoded English strings that exist nowhere in `strings.xml` or `strings-fr.xml`: `"kiosk on (5
apps)"`, `"missing pkg"`, `"missing schedule"`, `"failed"`, or — on a real failure — whatever
`Throwable.message` an Android `SecurityException`/`IllegalStateException` happens to contain
(`CommandExecutor.kt:41,48-49,52,55,60,64,75-76`). The parent sees something like **"OK: kiosk on
(5 apps)"** or **"Erreur : missing pkg"** — English developer shorthand glued onto a translated
"OK"/"Erreur" prefix, on the French *or* English side, on what is otherwise a carefully
bilingual, jargon-free app (the project even has a test enforcing key-for-key string parity).

**Why it matters.** This isn't an edge case — it fires on the single most common parent
interaction (turning child mode on/off, locking the phone, choosing apps). A French parent who
never learned the English word "kiosk" gets it thrown at them the first time they toggle child
mode. It directly contradicts the project's own "family vocabulary, never MDM jargon" rule, and
it's the most visible copy problem in the app because of how often it appears.

**Fix.** Stop echoing `r.msg` to the parent UI. Map `cmdId` (or `CmdType`, already known at the
call site since `ControllerViewModel` issues the command) to a small set of new, translated result
strings — e.g. `child_result_kiosk_on`, `child_result_locked`, `child_result_error_generic` — add
them to both `values/strings.xml` and `values-fr/strings.xml`, and reserve the raw `msg` for
`Log.d` only (it already has a log line for the ignored-result case at `ControllerViewModel.kt:73`
to model this on). A generic "Something went wrong, try again" is better than leaking an exception
message to a non-technical parent.

## 2. "Stop child mode" has no confirmation — every other risky action in the app does

**Screen:** `parent-device.png`, the filled "Stop child mode" button at the bottom of the Content
card.

**The problem.** `DeviceScreen.kt:166-168`:

```kotlin
Button(onClick = { if (s?.kiosk == true) viewModel.kioskOff(deviceId) else viewModel.requestApps(deviceId) }, Modifier.fillMaxWidth()) {
    Text(stringResource(if (s?.kiosk == true) R.string.child_stop else R.string.child_start))
}
```

One tap on the most visually prominent button on the page (filled, not outlined) instantly
removes every restriction from the child's phone — no `AlertDialog`, no undo. Compare this to the
same app's own pattern for other consequential actions: removing the parent PIN
(`SettingsPinScreen.kt:60-71`, with copy explaining exactly what changes) and regenerating the
pairing key (`SettingsAdvancedScreen.kt:59-76`, same pattern) both get a confirm dialog with
specific, honest consequences spelled out. Stopping child mode is arguably the single most
consequential toggle on the child's device page, and it's the one action in this set with no
confirmation at all.

**Why it matters.** A parent scrolling the device page (the Content card sits directly above two
other outlined buttons — "Change" and "Choose allowed apps…") can mis-tap the filled button below
them and instantly hand the child mode's full app list, with no warning and no easy way to tell
it just happened besides re-checking the page.

**Fix.** Wrap the `kioskOff` call in the same `AlertDialog` pattern already used for
`pin_clear_warning`/`regenerate_key_warning`, with a plain-language string, e.g. "Your child's
phone will go back to a normal phone: no app limits, no allowed-apps list. You can turn it back on
any time." Add the new key to both locale files.

## 3. The header long-press has no confirmed accessible equivalent

**Screens:** `child-launcher-childmode.png`, `child-launcher-allapps.png`, `child-bedtime.png` —
none show any visible affordance for the gesture that opens the parent PIN pad / parent menu, by
design.

**The problem.** The long-press is implemented with raw pointer input rather than Compose's
standard long-click affordance:

```kotlin
// ChildLauncherScreen.kt:126-131
.pointerInput(Unit) {
    detectTapGestures(
        onPress = { vm.headerPressed.value = true; tryAwaitRelease(); vm.headerPressed.value = false },
        onLongPress = { vm.pinDialogOpen.value = true },
    )
}
```

`BedtimeScreen.kt:85-88` does the same. A `contentDescription` is attached to the header (good —
it labels the region), but `detectTapGestures` is not the same mechanism as
`Modifier.combinedClickable(onLongClick = …)`: Compose only auto-registers an accessibility
long-click action (and TalkBack's "double-tap and hold to activate" hint) for the latter. With raw
`pointerInput`, nothing tells a screen-reader user this region has a long-press action, or that
one exists on the screen at all — they'd have to already know the gesture and rely on TalkBack's
touch-passthrough to land it blind.

**Why it matters.** This is the *only* way onto the parent PIN pad, and therefore the parent
menu, pause, and re-pairing — for the entire time the phone is in child mode or bedtime-locked.
If a blind parent (or a child using TalkBack) genuinely cannot discover or trigger it, they have
no way into any parent-side control on that phone.

**The deliberate invisibility itself is defensible** — the code comments make a real case for it
("kids can't discover it by sight," and the bounce-suppression logic in
`ManagedViewModel.headerPressed` shows real care was taken to make the long-press actually
completable). The issue isn't that it's hidden from sighted kids; it's that hiding it from sight
also appears to hide it from the accessibility action model, which is a different and
narrower requirement.

**Question:** I could not verify with a live TalkBack session whether "explore by touch" +
"double-tap and hold" successfully forwards a raw touch sequence into `detectTapGestures`'
`onLongPress` in practice — Android's touch-exploration passthrough may make this reachable even
without a declared semantics action, just undiscoverable and unannounced. Worth a real TalkBack
pass before deciding how much to change.

**Fix, if confirmed.** Use `Modifier.combinedClickable(onClick = {}, onLongClick = {…})` (adjusting
`headerPressed` timing around `onClick`/`onLongClick` instead of `onPress`/`tryAwaitRelease`), or
explicitly add a semantics long-click action alongside the existing `contentDescription`, e.g.
`Modifier.semantics { onLongClick(label) { vm.pinDialogOpen.value = true; true } }` layered onto
the existing pointer input, so TalkBack both announces and can trigger it.

## 4. The drawer button is announced as "Back", and opens a menu titled "Controller"

**Screen:** `parent-children.png`, hamburger icon top-left.

**The problem, part one — wrong description.** `BasicLayoutWithTopBar.kt:56-61` hardcodes the
navigation icon's content description to "Back" regardless of what icon is actually shown:

```kotlin
navigationIcon = {
    if (leftAction != null) {
        IconButton(onClick = leftAction) {
            Icon(leftActionIcon, contentDescription = stringResource(R.string.back))
        }
    }
},
```

`Layout.kt:84` passes `Icons.Filled.Menu` as `leftActionIcon` for the drawer variant used on the
main "My children" screen, but the description stays "Back"/"Retour". A TalkBack user on the
parent's home screen hears "Back" for a button that doesn't go back — it opens a side drawer.

**The problem, part two — jargon in the drawer itself.** `Layout.kt:39,57` renders `drawerName` as
a large `titleLarge` header at the top of that drawer. `MainActivity.kt:109` supplies it from
`R.string.main_drawer_name`, whose value is **"Controller"** (EN) / **"Contrôleur"** (FR) — the
one place in the app's parent-facing UI where the raw MDM word for "the parent's device" leaks
through, right next to careful, deliberately non-technical strings like "My children" and "Night
lock" everywhere else.

**Why it matters.** Both are small, but they sit on the very first screen a parent (or their
screen reader) opens, and the second one directly violates the project's own copy rule.

**Fix.** Add a `leftActionDescription: String` parameter to `BasicLayoutWithTopBar` (default to
the existing "back" string; have `Layout.kt` pass a new "open menu" string instead when using
`Icons.Filled.Menu`). Add the paired string to both locale files. Separately, rename
`main_drawer_name` to something a parent would recognise — even just the app name — since the
drawer currently holds only two items ("My children", "Pair a device") that already duplicate the
FAB and are one tap away regardless.

## 5. A partially-restricted child gets no hint that anything is hidden

**Screens:** `child-launcher-allapps.png` (10 apps, unrestricted) vs.
`child-launcher-childmode.png` (same device, 5 apps, restricted) — visually, the second is simply
a shorter grid with nothing else different.

**The problem.** `ChildLauncherScreen.kt:181-197` only shows explanatory text
(`launcher_no_apps`, "No app allowed yet. Ask a parent.") when the allowed list is completely
empty. The moment even one app is allowed, that message disappears and the grid just... has fewer
tiles than the child remembers. There is no persistent "5 apps allowed" caption, no visible signal
that the launcher is in a restricted state at all versus simply having fewer apps installed.

**Why it matters.** This is exactly the case the review brief calls out: "when something is
blocked, does the child understand why, and what they can do about it?" A child who had Instagram
yesterday and doesn't see it today has no on-screen way to learn "a parent removed this" versus
"something's wrong with my phone" — and with a PIN set, they cannot reach the parent menu (which
*does* show `menu_child_mode`/`child_allowed_apps`, per `ChildMenuScreen.kt:76-82`) to check,
because that screen is gated behind the same PIN their parent holds.

**Fix.** A small, low-key, always-present caption under the header — even reusing
`child_allowed_count` ("5 allowed") the same way the parent-side "Allowed apps" dialog already
phrases it — would tell a child their launcher is intentionally curated without turning the screen
punitive or nagging. This doesn't need a new string category; it needs the existing
`child_allowed_count` pattern surfaced here too.

## 6. The "children visible" status dot on the parent's home screen is color-only

**Screen:** `parent-children.png`, the dot next to "1 connected" in the top bar.

**The problem.** `OnlineIndicator.kt:23-28`:

```kotlin
val color = if (advertising) Color(0xFF2E7D32) else MaterialTheme.colorScheme.error
Row(...) {
    Spacer(Modifier.size(12.dp).clip(CircleShape).background(color)); ...
    Text(stringResource(R.string.children_online_count, online), ...)
}
```

The dot has no `contentDescription`, and the adjacent text only ever states a connection *count*
("1 connected") — it says nothing about whether the phone is currently discoverable to children at
all. Compare this to the functionally identical dot on the child's own launcher header
(`ChildLauncherScreen.kt:150-158`), which does carry a `contentDescription` distinguishing "online"
from "offline". The parent-side dot is the one place in the app where a piece of state is
communicated by color alone.

**Why it matters.** A colorblind parent, or one using TalkBack, gets no signal that "Visible to
children" (the switch just above, `DevicesScreen.kt:64-65`) is off — which is the actual cause of
a child failing to connect, and the scenario `ServiceBanner.kt` is designed to warn about
separately.

**Fix.** Add `.semantics { contentDescription = … }` to the dot describing the discoverability
state, mirroring `launcher_online`/`launcher_offline`'s pattern with new strings such as
`conn_indicator_on`/`conn_indicator_off` (or reuse `children_visible` + `conn_yes`/`conn_no`) in
both locale files.

## 7. Device-page actions look identical whether the child is online or offline

**Screen:** `parent-device.png`.

**The problem.** Every action button on `DeviceScreen.kt` (Lock now, Choose allowed apps, Install,
Add Google account, Refresh, Change content restrictions…) renders the same regardless of
`isOnline`. The only offline feedback is a one-shot snackbar, "This device is offline"
(`ControllerViewModel.kt:206`, `child_offline_msg`), that fires *after* a tap. There's no
persistent visual cue on the page itself.

**Why it matters.** This is squarely the brief's "state that is hard to read at a glance." A
parent working through several changes on a phone that went out of range gets a string of
snackbars rather than one clear "this device isn't reachable right now" signal, and might not
notice any of them if they're scrolling.

**Fix.** Either disable the action buttons (with the existing `AccentPill`'s online/offline colour
already computed at the top of the screen) or add a persistent inline banner reusing
`ServiceBanner`'s pattern for "this device is offline — changes will apply once it reconnects" (BLE
commands are fire-and-forget here, not queued, per `ControllerViewModel.kt:206`, so the wording
needs to reflect that they won't retry automatically).

## 8. Screenshot/code mismatch: "Connection" settings row

**Screen:** `parent-settings.png`, described in the README and visible in the image as
Appearance & language / Parent PIN / Advanced only.

**Question — likely stale screenshot.** `SettingsCategories.kt:47-51` and
`Routes.kt` (settings) both show a fourth row, "Connection" (`Icons.Outlined.Share`,
`settings_connection`), sitting between Parent PIN and Advanced, unconditionally rendered. I found
no code path that would hide it. Either `parent-settings.png` predates that screen being added, or
there's a build/branch mismatch I didn't find. Worth confirming before treating the screenshot
index as current documentation.

**Separately, a real (minor) inconsistency**: of the four category rows, three
(Appearance, PIN, Advanced) pass a one-line `supportingText` explaining what the screen does;
Connection (`SettingsCategories.kt:47-51`) does not. Given `SettingsConnectionScreen.kt` is one of
the more technical screens in the app (BLE advertising state, event log), it's the one that would
benefit most from a plain-language subtitle, e.g. "Which children are connected right now." Add
`settings_connection_help` to both locale files.

## 9. Question: child parent-menu screenshot theme looks inconsistent with the rest of the child side

**Screens:** `child-parent-menu.png` (plain light background, default-looking blue accents) vs.
`child-launcher-childmode.png`, `child-bedtime.png`, `child-pin-dialog.png` (all dark, softly
accent-tinted).

`ManagedThemed` (`ui/UiPrefsState.kt:63-67`) wraps every screen in `ManagedHomeActivity` — launcher,
bedtime, and the parent menu alike — in the same `ThemedByPrefs`, driven by the same pushed
`ChildPrefs`. I couldn't find a code path that would theme `ChildMenuScreen` differently from its
siblings, so this is most likely a capture-time artifact (theme prefs changed between screenshots,
per the README's own recapture caveats) rather than a real bug. Worth confirming on a fresh
capture, since if it *is* real it would be a jarring light/dark flash for a child who long-presses
into the menu at night.

## What's genuinely well done

- **Honest, unhedged safety copy.** `safety_explain` ("Browser settings only apply to Chrome...
  Restricted Mode hides most mature content, not all of it") is the rare parental-control string
  that undersells rather than oversells what the feature does. `appcfg_none` does the same for
  per-app settings that don't exist. This is exactly the tone the brief asks for.
- **The bedtime emergency exit is real, not decorative.** `BedtimeScreen.kt:103-112` and its
  backing comment in `ManagedViewModel.openEmergencyDialer` document that this was added after
  finding the assumed power-menu route doesn't exist on real hardware (Samsung/Android 14). It's
  deliberately placed outside the long-press column so reaching for it can never trigger the PIN
  pad by accident. This is careful, tested, safety-first engineering, not a checkbox.
- **PIN brute-force handling is proportionate.** Exponential backoff capped at 60s, persisted
  across process death so force-stopping the launcher can't reset it (`ManagedViewModel.kt:40,
  116-123, 222-227`), with a visible countdown rather than a silent lockout — protective without
  reading as punitive.
- **Two of the app's most consequential actions already get real confirmation dialogs** with
  specific, honest consequences spelled out in plain language (`pin_clear_warning`,
  `regenerate_key_warning`) rather than a generic "Are you sure?" — this is the pattern Finding 2
  above asks to extend to "Stop child mode."
- **Contrast math, not guesswork.** `Palette.luminance`/`isLight` implement actual WCAG relative
  luminance rather than a naive brightness threshold, and it drives both text-on-accent color
  choices and the status/nav bar icon style (`SystemBars` in `UiPrefsState.kt`) — the accent-color
  picker was clearly built with light/dark contrast in mind from the start.
- **Bilingual parity holds.** Both `strings.xml` files are 300 lines, key-for-key identical sets —
  the test enforcing this is doing its job (Finding 1 is a leak *around* the resource system, not a
  parity gap within it).
- **The child launcher reads as a kid's phone, not a locked enclosure.** Big rounded pastel tiles,
  a press-bounce, a soft accent gradient, a time-of-day greeting — `AppTile.kt` and
  `ChildLauncherScreen.kt`'s own doc comment explicitly targets "friendly for kids up to ~14, not
  toddler-cartoonish," and the screenshots back that up.
- **The parent menu explains itself with no parent in range.** `ChildMenuScreen.kt`'s doc comment
  ("still answers 'why is this phone behaving like this?' when the parent is nowhere in range") is
  exactly the right design goal for the brief's "does the child understand why" question, and the
  implementation (all state read from local prefs, not requiring a live BLE link) delivers on it.
